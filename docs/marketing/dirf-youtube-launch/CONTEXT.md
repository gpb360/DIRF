# Launch context

## Objective

Create five useful, long-form YouTube videos that make DIRF understandable,
credible, and easy to try. Each video must teach one complete idea, show real
product evidence, and create several self-contained Shorts without turning the
long-form episode into a string of disconnected hooks.

## User-visible success criteria

The package is ready when Gary can open any script, record the narration in one
session, follow the matching capture instructions, and hand the assets to an
editor without another strategy meeting.

The full series must answer:

1. What recurring agent-work problem does DIRF solve?
2. What happens from task description to routed workflow and verified handoff?
3. Where does DIRF fit beside Spec Kit, BMAD, GSD, and Superpowers?
4. How can one workflow stay useful across Codex, Claude, Cursor, other hosts,
   and a person?
5. How does DIRF hold up across multiple real projects, sessions, and worktrees?

## Primary audience

**The multi-agent operator:** a developer, technical founder, consultant, or
small agency lead who already uses two or more AI coding environments and has
accumulated skills, agents, prompts, worktrees, and half-finished handoffs.

Their urgent problem is not access to another model. They need repeatability:
the right workflow for the task, less context waste, state that survives a
session change, and honest evidence before “done.”

## Secondary audiences

- Engineering leads introducing agent workflows without forcing one vendor
- Skill and workflow authors who need discoverability and progressive loading
- Agencies repeating delivery patterns across client repositories
- Non-developer operators using agent hosts for research, marketing, and ops

## Audience exclusions

The first series is not aimed at viewers who want a one-click autonomous app
builder, a new programming framework, or guaranteed production deployment.
DIRF prepares and records the route. The agent host still performs the work,
and consequential actions remain under human authority.

## Voice

Direct, honest, practical, and lightly humorous. Explain the mechanics without
talking down to the viewer. Admit where DIRF ends. Avoid inflated productivity
claims, fake urgency, and vague claims such as “revolutionary” or “seamless.”

## Settled production decisions

- Five 16:9 episodes, each targeting 8–12 minutes.
- Gary's recorded voice is the preferred launch voice because founder-led proof
  is stronger than an anonymous synthetic narrator.
- Kai or an existing approved voice system is a fallback after script approval;
  voice generation remains a separate, cost-aware action.
- Visual language: live terminal capture, restrained motion graphics, and one
  reusable Excalidraw system map. Product truth leads; decoration supports it.
- Each episode supplies five Shorts candidates, for 25 total before performance
  pruning.
- One CTA per episode: view the repository and run the matching first command.
- No publishing, scheduling, voice generation, or paid rendering is authorized
  by this planning attempt.

## Proof available now

- Live `dirf flow` routed a PR-review request to installed code-review,
  security-review, and testing capabilities.
- Live `dirf status` identified the current branch, changed paths, exact latest
  attempt, and upstream drift.
- Live `dirf portfolio --json` reconciled nine registered projects and their
  attempt lifecycle state from one central store.
- Current `origin/main` documents zero runtime dependencies, host-neutral
  attempts, canonical cross-worktree state, progressive disclosure, portfolio
  exports, an MCP surface, and governed execution.

These are product-operation examples, not public customer adoption claims.
